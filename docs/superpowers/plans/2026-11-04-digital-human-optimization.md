## 第一阶段：播放、打断与服务恢复

### 任务 1：复核锁外视频解码，对应问题 1

范围为 `backend/transport/photo_timeline.py`、调用方 `photo_webrtc.py` 和 `photo_session.py`，以及 `tests/test_photo_timeline.py`、`test_photo_webrtc.py`、`test_photo_session.py`。不改变外部时间轴接口。

先复核现有未提交实现。PCM 锁只保护播放位置、代际和读取器登记。解码不能持有 PCM 锁；正在解码的片段不能提前关闭。正常结束、解码异常、连续打断及多个读取者均必须最终释放读取器和文件。保留视频发送端的旧代丢弃、背压和单调时间戳检查。

验收使用已有慢解码回归，包括成功、异常和两个读取者的场景。PCM 读取和打断不能等待解码释放事件，现有 80 毫秒测试门限不放宽。该门限只用于隔离回归，不代表真实音频允许每次停顿 80 毫秒。重新检查视频时间戳不重复、不倒退，关闭后无读取器登记和临时媒体泄漏。

补查普通片段切换与关闭期间仍有读取者的情况。最后一个读取者退出后，片段只关闭一次；代际已失效的解码结果不能入队。画面和 PCM 时间点必须取自同一次快照，不能在解码完成后重新读取时间点。慢关闭与文件删除也不能退回 PCM 锁内。

主要风险是锁外解码期间关闭文件，或返回了错误播放位置对应的画面。出现任一问题，停止后续性能改动，先修正资源寿命和快照一致性。

### 任务 2：复核语言模型请求取消，对应问题 2

范围为 `backend/transport/photo_session.py`、`backend/dialogue/client.py`，以及 `tests/test_photo_session.py`、`test_client_scheduling.py`。不修改现有 HTTP 路径、回答格式或情感字段。

保留当前直接等待回答请求的改法。打断、替换问题和关闭会话时，取消应传入该请求；旧回答不能继续写入对话历史、字幕或播放队列。声音、照片、线程任务仍按原规则接管迟到结果，不能批量删除 `_model()` 的取消保护。

先运行已有取消回归，再补查“旧请求取消后，新问题正常完成”。关闭不能等待被测试替身挂住的语言模型请求；原有迟到视频读取器回收测试仍须通过。随后用真实 llama-server 检查断开客户端是否停止旧推理；若未停止，记录服务端行为并单独处理，不把 HTTP 等待取消等同于计算已终止。

### 任务 3：修复进程登记失败的回滚，对应问题 3

范围为 `scripts/services.py`、`tests/test_service_shutdown.py`、`test_photo_runtime.py` 和 `test_cleanup_services.py`。保留启动命令、进程身份校验及只管理本项目进程的限制。

新增“创建进程成功、写入管理记录失败”的故障注入测试。记录写入失败时，使用刚取得的进程句柄和本次创建的进程组直接回收，并等待退出；随后回滚本次已登记的服务。不能只移动 `launched.append()`，也不能依赖磁盘上不存在的记录。清理错误应保留原失败原因，并明确报告尚未退出的进程；不得扫描并杀死未知占用端口的进程。

本次创建的句柄必须在 `Popen` 返回后立即纳入内存中的归属记录，再尝试写盘。异常回滚和 `KeyboardInterrupt` 均只回收本次创建的进程；此前已运行的服务保留。记录写入失败与回滚失败同时发生时，保留原异常，并输出尚未退出的 PID、命令和清理错误，不用第二个异常覆盖第一个异常。

验收要求模拟磁盘满和记录写入失败时，没有本次新建的失管进程；此前已运行的服务不被误停。既有 PID 重用保护、停止超时保留记录和端口释放测试仍须通过。

增加同一故障点首次失败、修复后重试的检查，确认未遗留端口或错误登记。服务启动的 180 秒和停止的 20 秒门限保持不变，但耗时统一使用 `backend.clock.monotonic()`；普通系统单调时钟变慢时，实际等待不能随之拉长。对应假时钟测试也应切换到实际使用的时钟入口。

### 任务 4：统一新旧服务的就绪检查，对应问题 6、7

范围仍为 `scripts/services.py` 及上述服务测试，不改模型下载模块。

新启动和复用的服务都必须通过相同的健康检查。PID 存活只代表进程存在，不代表可以提供服务。复用服务检查失败时应报告具体服务及原因，不能打印全部启动成功，也不能随意停止本次调用之前已存在的进程。

健康检查只要求接口可用；声音和照片服务的 `loaded=false` 是合法冷状态，不能为通过启动检查强制加载模型。新进程仍在 180 秒内轮询，单次请求最多两秒且不超过剩余期限。已有进程执行一次同样的健康请求，失败则明确退出，保留此前的进程归属。

本地健康请求使用禁用代理的标准库 opener，仅作用于回环地址。下载请求继续保留原代理行为。已有测试中“正确进程不重复启动”的替身需要同时模拟健康响应，不能为了通过测试而跳过就绪检查。

增加三类回归：已有进程存活但不健康、中断首次启动后重试、存在 `http_proxy` 且没有 `no_proxy`。验收要求未就绪时明确失败，健康服务不因环境代理被误判，本来运行正常的服务不重复创建。

## 第二阶段：识别初始化与首段语音延迟

### 任务 5：避免重复加载识别模型，对应问题 5

范围为 `backend/dialogue/client.py`、语音调用方 `backend/transport/photo_session.py` 和现有会话测试。可新增一个小型 `tests/test_dialogue_lifecycle.py`，专门检查识别模型的初始化寿命，不增加生产模块。

在同一 `Dialogue` 实例内，用实例级锁保护首次初始化，并在锁内再次检查识别器。初始化失败后允许明确重试，不能缓存半初始化对象。保留当前 CPU、int8、本地离线模型和中文识别设置。不要扩大为全局模型管理框架。

锁只覆盖识别器首次创建和发布。等待线程不能在未完成初始化时取得识别器。本任务不承诺跨会话只加载一次，也不默认将识别模型改为全局常驻；断开重连的装载成本应在任务 6 单独记录。

使用可阻塞的模型构造替身，同时启动两个识别调用，断言只构造一次。再检查第一次加载失败后可重试、打断后旧识别结果不进入新一轮。不要仅凭初始化加锁就声称所有识别过程已线程安全；如实际识别存在争用，再依据复现决定是否串行化识别。

### 任务 6：先测量再降低等待，对应问题 4

范围为 `photo_session.py`、`dialogue/client.py`、现有声音和照片客户端、`scripts/acceptance.py`，必要时涉及 `frontend/src/native-audio-output.ts` 的诊断路径。复用 `backend.clock` 和已有验收产物，不新建监控服务。任何新增诊断字段必须保留现有字段和消费者。

先完成计时，再选择性能改动。服务端使用 `backend.clock`，接收端使用自己的单调时钟计算本地时长；不得直接相减 WSL、Windows 和浏览器的绝对时间。最小计时项为识别、语言模型、声音请求、照片请求、首次入队、首次非静音接收和整轮耗时。识别项对文字输入标为不适用，不写为成功耗时零。

自动延迟主指标定义为：验收接收端从发送本轮问题，到收到本轮首个非静音音频帧的时长。复用现有 PCM 非静音判断，按 generation 归属并排除旧轮次；超时和错误请求保留在结果中，不能只统计成功样本。完整轮次时长与首声时长分别记录。

文字输入从发送 `chat_text` 起计；语音输入从发送 `stop_recording` 起计。语音录制与上传时长另列，不混入说完话后的等待。服务端相应从收到这两个控制消息起计，语音轮次的开始时间须跨越识别与后续回答阶段保留，不能在识别结束后重新起表。

正常延迟样本必须串行执行。发问前确认接收端连续半秒静音，保存发送时间，再用该轮 `turn_complete` 的 generation 归档；不能仅靠一个累积音频帧计数跨轮归属。打断和恢复样本单列，不混入正常请求的延迟分布。

浏览器持续接收待机静音，因此连接成功、`audio.playing`、收到首个音频包或“正在播放”状态均不能作为首声证据。浏览器侧若能提供首个非静音片段的预计播放时间，应单独标为估计值；无法取得时记为未测。实体扬声器是否实际出声仍需试听，不能与自动首声接收指标混用。

区分 HTTP 请求总耗时与 worker 报告耗时。现有 `generation_seconds` 包含部分等待和装载，且返回报告后还可能卸载模型，不能称为纯推理时间。必要时在现有 worker 内增加 GPU 等待、装载、推理和卸载的分项测量。最近一轮计时可作为会话指标的可选字段；测试报告保存完整样本，不在服务内保留无界历史。旧指标和响应字段保持兼容。

会话指标新增可选 `last_turn_timing`：包含 `generation`、`input_kind`（`text` 或 `audio`）、`status`（`running`、`completed`、`interrupted` 或 `failed`），以及毫秒单位的 `asr_ms`、`llm_ms`、`tts_first_ms`、`portrait_first_ms`、`first_enqueue_ms` 和 `total_ms`。前两项模型耗时分别为识别与语言模型等待；中间两项仅计首句请求；入队及总耗时从该轮开始计。未执行或尚未结束的阶段为 null，旧轮次的迟到完成不能覆盖新轮次指标。接收端的 `first_non_silent_receive_ms` 只写验收报告，不伪装为服务端测量值。

计时回归覆盖文字与语音、打断、失败和迟到完成，检查阶段次序与代际归属。只用可控时钟验证计时逻辑，不在普通单元测试中运行模型或断言真实首声秒数。

在相同硬件、电源方案、照片、参考声音及模型配置下，使用固定问题组进行配对比较。文字与语音分别测试，语音使用相同的预录 WAV。每个版本至少三个独立冷启动样本和二十次预热请求；预热问题组为十个问题各运行两次，版本执行顺序交替，测试期间不运行其他验收或 GPU 作业。

冷启动指重新启动本项目进程后尚未调用模型，不要求清空系统磁盘缓存，也不结束其他程序。分别报告冷启动样本及中位数、预热首声时长的中位数和 P95、总轮次耗时、CPU 内存及系统显存峰值。P95 用最近秩法计算，并给出样本量；二十次样本只能提供初步判断。历史的 207 秒和 22 秒只作背景，不作为这组比较的基线。

另列服务启动到就绪、显式模型预热和首请求等待三段耗时；调用方看到的总等待也须记录。比较基线取任务 0 至任务 5 通过后的版本，候选版只增加一个性能因素。保存两版实际源码差异，在隔离副本中切换，不用重置当前脏工作区来做对比。

声音或照片组件的对比固定回答文本、情感和音频。完整链路保留真实回答，并记录实际首句字数、完整回答字数和语音时长，避免将随机生成的短回答误记为实现提速。首句提示词改动另查内容是否完整，不能只比较耗时。

只实施测量支持的最小优化，一次只改变一个因素。优先比较识别冷加载、GPU 反复装载和首句整段生成的占比。预热或调整首句的方案应分别试验；未取得同口径改善证据时，只交付计时和瓶颈报告，不标记提速成功。预热成本计入冷启动报告，不能挪到用户等待之外后从总耗时中扣除。调整首句时保留其余回答，不直接截断内容，并检查回答完整性和声音接缝。流式方案作为后续独立决策，不纳入本批默认实现。

本阶段不默认引入流式语言模型解析，不让两个 GPU 模型未经测量同时常驻，不降低画面帧率或删减回答来制造提速。若需要这些变更，应停止并提交新的范围说明。

验收时，预热首声接收时长的中位数应下降，P95 不应劣于同批基线。若差异接近计时噪声，追加同样的二十次预热请求；仍不能区分时，结论为“未证明改善”，保留安全的计时实现，撤回本批独立性能改动。绝对秒数目标在新基线采集后确定，不承诺未经测量的倍数或“秒回”。其他质量门禁不变。

## 第三阶段：素材边界与界面反馈

### 任务 7：限制参考视频的解码预算，对应问题 8

范围为 `backend/media.py`、调用方 `prepare_voice()` 和 `backend/portrait/engine.py`，以及 `tests/test_media.py`、`test_photo_api.py`。先检查 `read_audio()` 的全部调用；参考视频限制不能误伤模型渲染读取生成语音的路径。

首版计划采用十分钟参考音轨上限，即 16 kHz 单声道最多 9,600,000 个解码采样。这是新增输入规则，不是当前已实现能力；同步 README、上传提示和失败说明。不得静默截断，超限时要求用户提供较短视频。文件大小限制仍保留；容器时长只作提示，不能单凭可能错误的声明时长拒绝或放行，实际输出采样计数才是最终边界。

解码过程中在保存或合并超预算采样前停止，不能先解码完再检查。保持当前六秒参考选择、源文件不变和声音确认规则。使用显式预算约束参考视频入口；共享读取函数的其他调用保留原约定。失败后，不能留下会被当成有效新参考声音的半成品。

接口采用 `read_audio(path, rate=16000, *, max_samples=None)`，默认行为保持兼容，只有 `prepare_voice()` 传入上述采样上限。重采样输出和 flush 尾部均计数。超限或解码失败须在写参考文件前结束。成功选段后，先写同目录唯一临时 WAV，再原子替换目标；写入失败清理临时文件，并保留已有参考文件。不得将文件替换称为 WAV 与人物 JSON 的跨文件原子事务。

已有且哈希有效的参考声音仍按原规则复用，不为新预算强制重解码或清理缓存。新增上限约束本次实际解码，不能据此废弃历史已验证素材。增加一个有效缓存不调用解码器的回归。

补测恰好达到上限、超过一个采样、flush 时超限、缺失或错误的容器时长、无音轨、少于六秒、临时 WAV 写入失败、现有参考文件保留及正常重试。用小预算替身验证提前停止，不在单元测试中分配长音轨。另查 `max_samples=None` 不限制模型渲染读取生成语音的路径。再用真实短视频确认正常素材行为不变。最坏内存上限同时计入 chunks、合并结果及类型转换副本，不能只按输入文件大小估计。
