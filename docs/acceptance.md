## 已修复的问题

- 对话请求使用必需的非空回答字段和受限情感字段。模型返回空 JSON 的失败已有真实复现和回归检查。
- 服务重启后，中断的准备任务会变为失败，并允许重试。有效缓存及声音确认状态会保留。
- 画面文件使用无损 RGB H.264。旧缓存会在再次准备时升级。待机视频最多缓存一百帧，每帧最大 1024×1024，缓存上限为 300 MiB。实际照片的十个相同相位，修复前后像素哈希一致。
- 验收截图写入、WAV 写入、句子视频打开和 HTTP 客户端创建已移出媒体事件循环。取消后才完成的视频读取器也会关闭，再清理文件。
- 打断会立即替换未发送的旧画面，保留原发送周期。补帧解码期间再次打断，也会保留补帧请求。两项回归均先复现超时，再验证修复。
- PCM 时间点重复时，重试只短暂等待，不推迟后续发送时间。迟到的替换帧也不会占用下一帧周期。两项回归分别复现了 400 毫秒周期被移到 405 毫秒，以及下一帧超时。每次重试仍会让出执行权，队列仍最多保留一帧。
- 验收进度报告也已移到后台线程。慢盘回归曾复现 255 毫秒的接收循环停顿。收尾会先关闭连接和会话，再等待旧报告写入，最后保存最终结果。
- 历史代的路径会在后台任务结束、文件清理完成后移出登记。仍有迟到任务或占用文件时，保留登记并继续清理。十轮二十个临时文件的回归，修复前触发 110 次删除检查，修复后为二十次。已被播放流程删除的文件不再重复发送删除请求。
- 视频解码按发送端进度推进。只有待发送画面被取走，系统才准备下一张画面。超过一个周期的旧画面会换为当前 PCM 对应的画面，替换不会消费额外周期。模拟发送器停顿 120 毫秒的回归，修复前十五帧耗时 641.7 毫秒，超出 610 毫秒门限；修复后通过。等待发送端取帧时，关闭检查也通过。队列上限仍为一帧。
- 视频编码线程保留一帧发送缓冲，25 FPS 下为 40 毫秒。刷新画面保留原发送时隙，音频节拍保持不变。回归测试注入 65 毫秒编码延迟，修复前发送间隔为 104.6 毫秒，修复后低于 90 毫秒门限。完整测试、独立代码复核、Chrome 检查和本轮连续验收均通过。帧率和音画差门限没有降低。
- 音频和视频使用同一 PCM 时间轴。解码停顿后，不会发送重复或倒退的视频 RTP 时间戳。
- 发现 WSL 普通单调时钟与 Windows 计时相差约 8%。内核跟踪显示，系统 WSL 的 chronyd 会调整 `tick`。原始单调时钟与 Windows Stopwatch 一致。播放节拍、运行时长和验收窗口现使用原始时钟。两路 RTP/RTCP 共用会话开始时建立的稳定 UTC 基准，避免系统调频和壁钟跳变破坏同步。代码没有固定倍率补偿，也没有降低帧率目标。

系统时钟排查期间的临时配置已恢复：原时钟源为 TSC，DigitalHuman 的网络校时服务已启动，Hyper-V 隐式校时参数为 Y。项目没有修改安装目录中的 aiortc 文件。
