# 照片数字人 · 项目技术讲解

这是一份"读完能改代码"的讲解，不是 API 手册。建议按章节顺序读：先建立全局时间轴，再分别看三个模型，最后看它们怎么被拼成一条不断流的播放链路。

代码结构见 [代码设计](architecture.md)，需求与验收见 [PRD](PRD.md)。

---

## 1. 一句话链路，以及它为什么慢

一次回答要经过六段：

```
文字/语音 → 对话模型（文字+情感）→ 语音合成 → 动作扩散 → 人脸渲染 → WebRTC 播放
   20ms       1.3–1.9s            3–5s/句     5.3s/6s音频   12.5s/6s音频   实时
```

用一句话概括这台机器的现状：**"想得快、说得慢、画得更慢"**。对话模型 1.3 s 就能给出首句，声音 6 s 左右能出第一句，但画面要 21 s 才能凑齐第一段——瓶颈完全在渲染。

所以整个项目的优化顺序是：

1. 先让回答**逐句**流出来，把"等整段"变成"等一句"（对话 SSE + 切句）。
2. 再让声音**分块**流出来，边合成边入队（CosyVoice 原生 stream）。
3. 最后让画面**分块**流出来，边渲染边配对（Ditto 稳定前缀 + 25 帧块）。
4. 用显存租约保证声音和画面能同时跑，不互相踢下卡。

## 2. 模型一：Ditto，把一张照片变成会说话的人

### 2.1 它到底做了什么

输入是**一张照片 + 一段 16 kHz 单声道音频**，输出是**25 fps 的人脸视频**，尺寸与照片等比（长边 ≤ 1024）。它不生成背景，只生成人脸区域，再贴回原图——所以衣服、背景、光线都保持原样，这也是"像本人"的关键。

六个组件，按数据流排列：

```
照片 ─► AvatarRegistrar ─► f_s（外观特征）、M_c2o（相机矩阵）、x_s_info（初始关键点）
音频 ─► Wav2Feat(HuBERT) ─► 每 40ms 一帧的音频特征
        Audio2Motion(扩散) ─► 动作序列（关键点 + 表情 + 头部姿态）
        MotionStitch ─► 与初始姿态拼接、眨眼、淡入淡出
        WarpF3D ─► 把人脸形变到目标表情
        DecodeF3D ─► 解码成 RGB 人脸
        贴回原图（mask 混合）─► 最终帧
```

### 2.2 三个容易误解的点

**第一，动作不是"跟着音频波形"生成的。** HuBERT 先把音频压成语义特征，扩散模型再在特征序列上生成动作。所以语速、停顿、重音会影响动作，但动作本身是"学出来的说话习惯"，不是物理仿真。

**第二，25 fps 是硬约束。** 音频侧所有窗口都按 25 fps 切：16 kHz 下每帧 640 个采样（40 ms），HuBERT 每次吃 6480 个采样（405 ms）、产出 5 帧、前进 3200 个采样（200 ms）——窗口重叠 50%，保证特征不跳变。

**第三，流式不能"算到哪发到哪"。** 扩散的 overlap 融合和末尾平滑会修正已经算出来的尾部。`MotionStream` 因此保留 `overlap_v2 + 6` 帧不发布，只把"再也不会被改"的前缀送出去：

```python
end = min(len(features), sequence.shape[1] - overlap_v2 - 6)   # 非最终
```

这也是为什么流式画面比整句模式"慢半拍"：它在等一个安全边界。

### 2.3 画质是怎么保住的

- 中间视频用 `libx264rgb` + `crf=0`：无损 RGB，随便 seek，块播完就删。
- 人脸区域用固定 mask 混合，背景不重算，所以不会出现"背景每帧轻微抖动"。
- 传输用 VP8，但关掉了噪声抑制、把最大量化步长压到 32，避免衣服纹理被当成噪声抹平。
- 码率按尺寸给：512 长边 4 Mbps、768 给 6 Mbps、1024 给 8 Mbps。

## 3. 模型二：CosyVoice 3，8 秒克隆一个声音

### 3.1 两条克隆路径：zero-shot 与 instruct2

CosyVoice3 有两条路，区别在于 LLM 看不看参考语音：

| 路径 | 进 LLM 的提示 | 音色来自 | 语气来自 |
|---|---|---|---|
| zero-shot | 参考语音 token + 参考文本 | flow（提示 mel + campplus 嵌入） | 参考语音本身 |
| instruct2 | 只有一句指令 | 同上 | 指令文本 |

`frontend_instruct2` 会显式删掉 `llm_prompt_speech_token`，模型听不到参考的节奏，只能照着指令说；zero-shot 保留这些 token，停顿、语速、音高起伏都更贴参考，代价是没法用"请非常开心地说"这类指令。

项目默认 `voice_clone_mode: hybrid`：

| 情感 | 路径 | 理由 |
|---|---|---|
| neutral | zero-shot | 日常回答占绝大多数，优先像本人 |
| happy / sad / angry | instruct2 | 指令能明确改变语气 |

zero-shot 需要参考音频的转写。CosyVoice3 的提示格式是 `You are a helpful assistant.<|endofprompt|>` 接参考文本，准备人物时用本地 faster-whisper 生成并写进 `voice.text`；没有转写（或不足 4 个字）时这条路径不启用，自动回到 instruct2。`voice_clone_mode` 写 `zero_shot` 会让情绪句也走零样本（最像，但情绪指令失效），写 `instruct` 则全程走指令（情绪准，音色略远）。

说话人缓存键因此带上路径与文本：

```
key = sha256(参考音频哈希 + 指令 + 模型修订 + 克隆路径 + 参考文本)
```

第一次 `add_zero_shot_spk` 后把说话人张量存成 `prompt-<key>.safetensors`，同一参考、同一情感、同一路径的第二句直接加载。

### 3.2 流式合成的三段

CosyVoice 的流式是"token → flow matching → HiFi-GAN"三段流水：

```
LLM 逐 token 出 ─► flow 逐块生成 mel ─► hift 逐块出波形
```

`stream=True` 时上游会按 `token_hop_len=25` 切块。项目在这里加了一层保护：包住上游的 `llm_job`，记录每个任务用的线程与异常，生成器关闭时先 drain 再 offload，并清掉 `tts_speech_token_dict` 等四张表。原因是上游的后台 LLM 线程不会因为 Python 生成器被 close 就停下，直接搬权重会踩到还在用的 CUDA context。

### 3.3 响度：一个整句一个增益

`SpeechNormalizer` 不是逐样本 AGC。它做三件事：

1. 用前 0.5 s 的有效语音估一个增益：目标 RMS 0.1，峰值不超过 0.891（约 -1 dBFS）。
2. 用 5 ms 前瞻的限幅器压住瞬态，释放时间 50 ms。
3. 整句共用这个增益。

好处是停顿不会被放大、语气动态保留；坏处是如果参考音频前半句特别轻，整句会偏响。参考片段的选择因此很重要，见 3.4。

### 3.4 参考音频：相似度的上限在这里

克隆的天花板由参考片段决定，模型只能复制它听到的东西。取样分四步：

1. **解码**：整条音轨按 24 kHz 解码，不再用 16 kHz。以前存成 16 kHz 再让模型升到 24 kHz，8 kHz 以上是空的——齿音和明亮度恰在这个频段。
2. **筛窗**：0.25 s 网格铺满全片，门限取本轨 p90 电平的 12%（旧版是绝对值 0.008，安静素材一个窗都过不了），并排除削波超过 1% 的窗。
3. **选代表**：得分最高的候选里均匀取 8 个窗做 campplus 嵌入，选离质心最近的一个。音乐垫底、第二个说话人、偏远麦克风位置都会偏离质心。
4. **整理**：去直流、首尾 10 ms 淡入淡出、把有效语音拉到 RMS 0.08（峰值 ≤ 0.95）。flow 直接吃这段 log-mel，电平偏低的参考会让生成的声音发薄。

量化验证用 `scripts/voice-similarity.py`：同一段音频自比是 1.000，同一人不同句子一般在 0.7 以上，换人通常掉到 0.6 以下。它用的是模型自己的 campplus 编码和 80 维 Kaldi fbank，与克隆时喂给 flow 的完全一致。

## 4. 模型三：Qwen2.5-3B，以及为什么让 emotion 排在 text 前面

对话模型跑在 llama.cpp 的 `llama-server` 上，Q4_K_M 量化、CPU 推理（`-ngl 0`）、6 线程、上下文 4096。选 3B 是为了不和显卡抢资源——它只要 CPU，画面和声音才能独占 GPU。

输出被约束成 JSON：

```json
{"emotion": "happy", "text": "今天天气很好，适合出去走走。"}
```

**字段顺序是有意的**：llama.cpp 按 schema 顺序生成，`emotion` 在前意味着第一个字段结束（十来个 token）就能确定语气，语音合成可以立刻用正确的指令开始，而不是先按 neutral 合成再返工。

`ReplyStream` 是一个逐字符状态机，专门处理三种"半截"：

- `\"` 被拆成两个分块 → 等齐再解码；
- `\u4e2d` 被拆开 → 等够 4 位十六进制；
- UTF-8 中文被拆开 → 按字符迭代，不按字节。

服务端如果忽略 `stream` 返回整段 JSON，同一个状态机照样能解析——这条降级路径保证换后端不会挂。

## 5. 为什么按"句"切，而不是按"字"

按字合成会让韵律破碎（每个字都要重新起调），按整段又太慢。句子是韵律完整、又能尽早开工的最小单位。

首句还额外做了一件事：**在 14 个字内遇到逗号就提前切**。

```
"今天天气很好，我们一起"  →  "今天天气很好，" + "我们一起去..."
```

只切第一句、只在已有标点处切、切完不增删任何字。这样首段从 20 字降到 8 字，TTS 与渲染的输入直接减半。

实测（本机 CPU 对话模型）：

| 问题 | 首段就绪 | 整段完成 | 提前 |
|---|---|---|---|
| 房间里的光线和气氛 | 1.33 s | 1.78 s | 0.45 s |
| 周末下雨适合做什么 | 1.27 s | 1.61 s | 0.34 s |
| 规律作息（无逗号可分） | 1.81 s | 1.81 s | 0 |

对话模型越快，收益越小；但在"边说边想"的长回答、或者换成更慢的模型时，收益是线性的——因为 TTS 与渲染和剩余解码是重叠的。

## 6. 三条"流"怎么对齐

### 6.1 句子流

`_pump_reply` 把 SSE 的文字喂给 `SentenceSplitter`，每闭合一句就放进 `ReplyFeed`。合成侧 `feed.get(index)` 拿到一句就开始，不用等 `done`。

`photo_streaming=false` 时这条流同样生效——所以即使不开流式音画，回答文字也是逐句出现的。

### 6.2 声音流

`/tts/stream` 每产出一块 PCM 就写进 `AudioSpool`，同时通过 NDJSON 告诉 studio "第 N 块、从第几个采样开始、多少采样、sha256"。studio 读到事件后再去读 `.npy`，校验范围与哈希。

为什么不在 NDJSON 里直接塞 base64 PCM？因为一块可能几百 KB，JSON 膨胀 33%，而且失去"文件落盘即可校验"的能力。

### 6.3 画面流

`/render/stream` 每 25 帧（1 秒）写一个 `video-N.mkv`，事件里带 `chunk_index`、`frame_start`、`frames`。studio 端强制要求 `frame_start` 连续、`1 ≤ frames ≤ 25`——缺一块就报错，不允许"跳过一块继续播"，否则音画会永久错位。

### 6.4 配对规则

48 kHz 下，一帧画面正好对应 1920 个采样：

```
1920 / 48000 = 0.04 s = 1 / 25 fps
```

所以一句可播的长度是 `min(已有采样数, 已有帧数 × 1920)`。这句代码是整个流式链路的地基：

```python
available_samples = min(len(pcm), frames * 1920)
```

只要这个不变，声音和画面就不可能越走越偏。

## 7. 时间线：让声音当主时钟

### 7.1 为什么不用墙上时间

墙上时间会被 NTP 调整、被 GC 暂停、被编码抖动影响。一旦某次抖动，音画就永久差几十毫秒。这里的做法是：

- 音频轨道每 20 ms 读 960 个采样（`read_audio(960)`），时间线把 `cursor` 往前推；
- 画面按 `cursor / 48000` 秒去当前 clip 里取帧；
- RTP 视频时间戳由音频采样换算：`pts = audio_samples * 90000 // 48000`。

声音是"消耗品"，播出去就回不来；画面是"查询品"，可以重复、可以晚到。所以让画面追声音，而不是反过来。

### 7.2 缓冲策略：宁可晚开，不要开一半断

流式首句启动要满足三个条件（`_enough_buffer`）：

1. 最近 3 个画面块的速率 ≥ 1.1× 实时；
2. 声音速率 ≥ 1.1× 实时；
3. 可播数据 ≥ 2 秒。

如果后面还有第二句，还要等第二句也缓冲够——否则第一句 1 秒播完，第二句还在渲染，用户会听到一段尴尬的静音。

中途供不上时，时间线暂停并记一次 `underruns`，界面显示"正在缓冲声音和画面"。这个计数是验收指标：正常对话应该是 0。

### 7.3 丢帧的五个原因

`PhotoVideoTrack.drop_reasons` 会分别计数，排错时非常有用：

| 原因 | 含义 |
|---|---|
| `stale_queued_generation` | 队列里的帧属于被打断的旧轮次 |
| `cleared_pending` | 打断时主动清掉待发帧 |
| `stale_decoded_generation` | 解码完成时轮次已经变了 |
| `pcm_retry` | 音频没前进，视频 pts 会重复，只能重试 |
| `queue_replaced` | 新帧覆盖了还没发出去的旧帧 |

如果 `pcm_retry` 很多，说明音频时钟被卡住（通常是合成或事件循环阻塞）；如果 `queue_replaced` 很多，说明渲染比 25 fps 快，传输端在丢帧——这时候该看码率和网络，而不是模型。

## 8. 两个模型怎么共用一块显卡

### 8.1 先理解"预热"到底做了什么

`warmup()` = `_activate()` + `offload()`。它把权重搬上卡、跑一次 CUDA 初始化、再搬回 CPU。收益有三个：

- CUDA context 建好，第一次推理不用再等 1–2 s；
- cuDNN/cuBLAS 的 kernel 选型与编译完成；
- 显存分配器预热，减少首次分配的碎片。

代价是启动多等 30–65 s（本机 voice 65.2 s、portrait 29.8 s）。所以它默认由 `start.ps1` 打开，但**不阻塞健康检查**——服务先可用，模型在后台热。

### 8.2 三种锁

| 锁 | 何时用 | 为什么 |
|---|---|---|
| 全局独占 | 准备人物、整句渲染 | 这些操作会长时间占满显存 |
| 会话共享 | 流式对话 | 允许同一会话的 voice/portrait 同时算 |
| 串行计算 | 显存不够时 | 一次只让一个模型上卡，靠时间换空间 |

会话租约的细节：先拿全局独占锁（排除准备任务），写 `lease.json`（session + 32 字节 token + pid 签名），再把锁降级成共享。这样本会话的两路 worker 能同时持有共享锁，而别的会话或准备任务进不来。

每次推理前都要重新校验 owner：token 用 `compare_digest`，pid 的 `/proc` 签名必须匹配。进程重启后 PID 可能复用，签名能识别出来。

### 8.3 准入测试不是拍脑袋

`.runtime/stream-admission.json` 由 `scripts/profile_streaming.py` 实测生成：同一会话里让 voice 和 portrait 同时跑几组长短句，采样空闲显存，记录双模型峰值增量。只有满足下面全部条件才算通过：

- 采样期间空闲显存从未低于 1 GiB；
- 记录里的 GPU UUID 与当前卡一致；
- `code_key` 与当前六个源码文件的哈希一致（防止改了代码还用旧结论）；
- `peak_delta + 1024 MiB ≤ 当前空闲`。

不通过就走串行。这不是保守，而是因为 OOM 的代价是整轮重来，比慢更伤体验。

### 8.4 串行回退的边界

只有"本轮还没有任何一句开始播放"才允许重试。一旦用户已经听到声音，显存不足就直接报错，不做"从头再来"——那会让体验更差。

## 9. 性能剖面

以下数据来自本机（单卡、WSL2、2026-11-07），只用于判断量级，不是承诺值。

### 9.1 整句渲染：6.02 s 音频 → 150 帧 / 27.6 s（约 4.6 倍慢于实时）

| 阶段 | 耗时 | 占比 |
|---|---|---|
| 逐帧渲染（stitch + warp + decode） | 12.47 s | 45% |
| 动作扩散 | 5.42 s | 20% |
| HuBERT 特征 | 3.78 s | 14% |
| 合成（贴回原图） | 2.98 s | 11% |
| 编码 | 1.02 s | 4% |
| 权重上卡/换入 | 1.06 s | 4% |

结论很直接：**逐帧渲染是大头，不是扩散**。所以 `frame_batch` 与 `frame_stride` 的收益比降采样步数更明显；再往下要走 ONNX/TensorRT 或换更轻的解码器。

### 9.2 首响（热启动、整句模式）

| 节点 | 时间 |
|---|---|
| 首字 | ~1.4 s |
| 首句文字 | ~1.6 s |
| 首句声音 | 6.6 s |
| 首句画面 | 21.0 s |
| 首段入队 | 34 s（该轮首段更长） |

### 9.3 浏览器音画同步（整句模式，非流式）

| 指标 | 值 |
|---|---|
| 采样 | 数十次/轮 |
| 最大偏差 | 52 ms |
| P95 | 39 ms |

这说明"以 PCM 为主时钟 + 音频换算视频 pts"的方案是对的：即使生成慢，同步也是稳的。流式模式还需要单独测这一项。

## 10. 调参手册

| 参数 | 默认 | 调大 | 调小 | 建议 |
|---|---|---|---|---|
| `portrait_sampling_steps` | 12 | 动作更稳、更慢 | 更快、可能抖 | 12–20；抖就加，卡就减 |
| `portrait_frame_batch` | 4 | 吞吐更高、显存更高 | 更省显存 | 4–8；OOM 会自动退回逐帧 |
| `portrait_frame_stride` | 2 | — | 1 = 全帧计算（最清晰最慢） | 2 是速度/画质折中；3 会明显发飘 |
| `first_clause_chars` | 14 | 首段更长、更自然 | 首段更短、开口更早 | 10–16；0 关闭 |
| `dialogue_streaming` | true | — | 整段生成，便于对比基线 | 除排错外保持 true |
| `voice_reference_seconds` | 8 | 更像、合成略慢（flow 的提示变长） | 更快、细节更少 | 6–10；低于 6 音色明显变粗 |
| `voice_clone_mode` | hybrid | — | — | 最像用 zero_shot，情绪优先用 instruct |
| `tone_voice` | true | 非自然语气的发音也生效，平语改走 instruct2 | 语气只改文案，音色最接近参考 | 想听出语气就开；只想最像就关 |
| `max_photo_variants` | 8 | 可存更多造型 | 省磁盘 | 单套约 32 MB |
| `portrait_seed` | null | 固定动作噪声，便于同机 A/B | — | 仅诊断，不承诺跨设备复现 |
| `photo_streaming` | false | — | — | 验收通过前不要开 |
| `dialogue.max_tokens` | 128 | 回答更长 | 更短 | 配合"最多两句"提示词 |

想回到"原始画质基线"：`steps=50, batch=1, stride=1`。这三个值每次渲染重新读配置，改完下一句生效，不用重启。

## 11. 排错手册

| 症状 | 先看什么 | 常见原因 | 处理 |
|---|---|---|---|
| 首句 30 s+ | `last_turn_timing.portrait_first_ms` | 渲染慢、显存换入换出 | 降 stride/steps；确认没有别的进程占卡 |
| 首声很慢但画面正常 | `tts_first_ms` | 冷启动、参考音频太长 | 用 `restart-and-warm.ps1`；参考 6 s |
| 声音断续 | `stream_underruns`、`paired_buffer_seconds` | 缓冲不足、合成速率 < 1× | 降步数；或退回整句模式 |
| 画面停顿但声音连续 | `drop_reasons.pcm_retry` | 音频时钟被阻塞 | 看事件循环是否有同步阻塞调用 |
| 音画越走越偏 | `diagnostics=1` 的偏差采样 | pts 重复、时间线被打断 | 检查是否发了重复 RTP 时间戳 |
| 显存不足 | `stream_fallback_reason`、准入文件 | 并行余量 < 1 GiB | 自动串行；或重跑 `profile_streaming.py` |
| 准备失败 | `job.error` | 参考音频太短/太吵、照片多张脸 | 换素材；照片只留一张清晰正脸 |
| 回答被截断 | `max_tokens`、`maxLength` | 128 token 到了上限 | 提示词约束"最多两句"或调大 |
| 浏览器没声音 | 音频元素状态 | 自动播放策略 | 点"开启声音" |
| 前端改了不生效 | `check_frontend` | dist 与源码不一致 | `npm run build` |

## 12. 个性化：语气、表情与造型

三个维度都只改"条件"，不改模型：语气改提示词与（部分）发音指令，表情改 Ditto 的情绪条件，造型换一张源照片和它的缓存。

### 12.1 语气：文案与发音是两条独立路径

- 文案：`system_prompt(tone)` 在固定基座中间插一句语气约束，硬规则（最多两句、不虚构、JSON 契约）留在末尾。3B 模型对末尾约束更敏感，顺序不能反。
- 发音：CosyVoice 的指令只有一份。非平语时情绪指令优先，语气只影响文案；平语时语气才占这个位置。
- 与克隆模式的相互作用：`hybrid` 下平语默认走零样本，而零样本不接收指令。所以 `tone_voice` 打开且语气不是"自然"时，平语句改走 instruct2；关掉则语气对声音无效。默认语气是"自然"，因此默认体验仍是零样本、最像参考。

| 情绪 | 文案 | 发音指令 | 首句缓存 |
|---|---|---|---|
| neutral + 自然 | 自然措辞 | 空 | 零样本，无变化 |
| neutral + 其他 | 语气措辞 | 语气指令 | instruct2，新增一个 speaker 缓存 |
| happy / sad / angry | 语气措辞（被情绪覆盖） | 情绪指令 | 与改动前完全一致 |

本机实测（同一个人物、同一句平语、8 s 参考音频）：

| 语气 | campplus 相似度 | 生成耗时 |
|---|---|---|
| 自然（零样本） | 0.775 | 5.07 s |
| 亲切（instruct2） | 0.675 / 0.722（两次） | 5.22 / 4.54 s |
| 专业（instruct2） | 0.746 | 6.28 s |

同参数两次生成相差 0.047，所以 0.05 以内的相似度差属于采样波动。结论：自然语气确实最像参考；选其他语气会用一点音色相似度换表达力，这与设计预期一致。

### 12.2 表情：软标签就是强度旋钮

Ditto 的 `emo` 是 8 类条件（Angry0…Contempt7），`_get_emo_avg` 对给出的索引做 softmax：给两个索引就是 50/50，给一个索引就是 one-hot 近似。项目四个预设：

| 预设 | `emo` | `exp` | 说明 |
|---|---|---|---|
| 自然 | 4 | 1.0 | 与改动前完全一致 |
| 微笑 | (3,4) | 1.0 | Happy 50% + Neutral 50% |
| 严肃 | Neutral 88% + Sad 12% | 0.75 | 软标签取向 + 更小的表情幅度 |
| 惊讶 | 6 | 0.85 | Surprise 单一标签，幅度略收 |

优先级：情绪非 neutral 时用情绪标签且 `exp=1.0`，预设完全忽略。用户选"微笑"不代表希望用笑脸播报坏消息。

注意 `use_d_keys['exp']` 不是"表情种类"，它缩放的是驱动信号里的表情增量幅度；只调它不会改变情绪方向，方向由 `emo` 决定。

### 12.3 造型与换装：改照片，不改渲染

重绘区域是 512×512 的头部裁剪框（scale 2.3、上偏 0.125），贴回时用 0.9 的软边方框。衣领以下、背景、光线都在掩码之外，是原照片像素。因此渲染期换装不可能，换装必须发生在准备之前：改源照片，再走一遍 `prepare`。

`backend/outfit.py` 的做法分四步（界面只暴露第 4 步的按图换装，前两三步仍可由 API 调用）：

1. **分割**：Segformer（clothes 版）给每个像素打标签，取 4（上装）与 7（连衣裙）。分割出的边界比真实轮廓往里缩 1–2 像素，直接换色会留下一圈原色描边，所以要把环带重新长回来——只长那些"更像衣服而不是皮肤"的像素（到衣服中位色的距离 ≤ 到皮肤中位色的距离）。
2. **换色**：转 Lab，把掩膜的色度换成目标色、亮度按中位数平移，褶皱和高光因此保留。两个坑：暗色（藏青、墨绿）在原亮度下会看成炭灰，所以目标 L < 32 时按 (32−L)×0.55 抬亮；a/b 不能和 L 一起 clip 到 0..100，否则所有蓝色都变灰——这是第一版真实踩到的 bug。
3. **换款式**：SD1.5 inpainting 重绘掩膜区域。直接把黑色 T 恤喂进去，模型会顺着深色上下文画出深色花纹；先把洞用新衣底色平填再扩散，颜色才跟得住提示词。默认 768 长边、36 步、引导 7.5，单张约 30 秒（含 12 秒模型加载）。
4. **按图换装**：把用户上传的衣服图裁掉白底，作为 IP-Adapter（plus, ViT-H）的 image prompt，缩放 0.9 注入；掩膜向外扩 3%，让外套的领子和肩线有地方长出来。两个实测细节：不填文字描述时模型会画出"带牛仔纹理的花衬衫"，补一句名词（翻译成本地模型的活）后才是真外套；负面词里不能留 `pattern/plaid`，否则会和参考图的织物纹理打架。

两条不变式：

- 掩膜外的像素逐像素不变（脸、颈部、背景），所以身份不会漂移；
- 结果是一套**新造型**，不是替换当前造型；要准备、要重连才生效。

模型来源：分割用 `mattmdjaga/segformer_b2_clothes`，修补用 `runwayml/stable-diffusion-inpainting`（CreativeML Open RAIL-M），都放在本地 `models/outfit/`，运行期不联网。

限制：源照片自带的水印如果压在衣服上，会被修补模型重绘成乱码；SD1.5 对衬衫领口的理解仍然偏弱，针织、大衣一类的纯色衣物更稳。换更好的修补模型只要把权重放进 `models/outfit/inpaint`。

### 12.4 标定：把"自然"变成数字

`scripts/expression_calibrate.py` 为同一段中性音频渲染四个预设，逐帧报告：

- 帧数与"自然"一致（25 fps 不因表情变化）；
- 变化像素占比 < 50%（没有整帧漂移）；
- 人脸区平均差 ≥ 1/255（可辨）；
- 掩膜外（alpha = 0）像素一致，容差 ±2（背景没被改动）。

前三条是硬门，最后一条用来发现"整帧重绘"这类回归。注意不要用"画面边缘"代替掩膜：这个头像的头部裁切框贴到照片顶边，边缘本来就在掩膜内，用边缘判定会误报。

本机实测（1024×1024 头像、1.96 s 中性音频、49 帧、`steps=12`）：

| 预设 | 变化像素 | 平均差 | 掩膜外 |
|---|---|---|---|
| 微笑 | 14.4% | 7.28 / 255 | 一致 |
| 严肃 | 8.4% | 6.03 / 255 | 一致 |
| 惊讶 | 17.7% | 9.64 / 255 | 一致 |

同参数连续渲染两次"自然"，逐像素差为 0，说明同一 worker 内输出稳定；跨进程、跨设备的复现仍未承诺（动作扩散、TTS 采样、对话温度都没有固定种子）。`serious` 的可辨性有数值支撑，但"看起来像严肃"仍要人工确认。

### 12.5 扩图：把半身照补成全身

扩图和换装共用一套 inpainting 管线，但出发点相反：换装只重绘"已经存在的衣服"，扩图要在**没有像素的地方**画出腿。SD1.5 没有任何三维概念，所以几何必须由代码算好，模型只负责"在指定区域按提示词作画"。

**先算身高。** 成年人大约 7.2 个头高。用分割标签里的头（帽、发、墨镜、脸）量出头部像素高 `head_h`，则人体底端应在 `y0 + 7.2 × head_h`。差值就是需要向下补的高度。三个边界条件：

- 原图已经切到发顶（`y0 ≈ 0`）时头顶预留为 0。补头顶等于让模型画头发，是降质最快的一步。
- 补的高度被夹在 `[0.06H, 2.2H]`：太少没意义，太多会把坐姿照拉成畸形长腿。**夹断时要告诉用户**：一张头部占画面 76% 的特写，按 7.2 头身需要补 5.5 倍画高，远超上限，实际只能得到七分身。所以 `plan_canvas` 会回传 `capped` 与 `predicted_gain`，界面据此提示"这次只能扩到七分身，要全身请换一张半身照"。不提示就等于骗人。
- 人物已经触底且估算不缺高度时直接返回 `already_full_body`，不生成、不建造型。

**再定掩膜：只给"人物走廊"。** 把整块 padding 交给模型，它会在背景里再画一个人；把走廊外的区域直接填好、不给模型机会，重复人的概率就下来了。走廊是以人物包围盒中线为轴、宽 1.18 倍身宽的竖直带，从**下摆**开始（不是从画布边缘开始）。从下摆开始这一点很关键：照片在半身处被裁断时，下摆与照片底边之间常有一段背景，若走廊从底边开始，生成出来的腿和衣摆之间会隔一条背景色横条。

**再决定填什么。** 背景用复制边缘（`BORDER_REPLICATE`）加模糊，再按离照片的距离淡到单一的背景色（照片四周 4 像素环的中位色）；走廊用下装中位色加竖向渐变。这里踩过一次坑：最初用镜像延展（`BORDER_REFLECT_101`），构图预览里人物的脸被复制到左右两侧和下方，模型会照着那些轮廓再画一个人。**填充不能复制人体**，背景宁可单调也不能有第二张脸。填色还能顺手产出一句提示词（"wearing navy blue trousers"），这是成本最低、收益最大的一条。

**接缝怎么处理。** 走廊从下摆开始，模型因此能直接接着衣摆画下去；拼合时只有掩膜内的像素用生成结果，掩膜外原样拷贝，接缝不会出现软边灰带。曾经设计过一个"接缝调色"步骤（Lab 空间增益/偏移对齐），后来去掉了：黑色上衣接浅色裤子本身就是合法的大色差，按颜色对齐会把裤子染成上衣的颜色，用颜色差做画质门也会把好结果判成 low。**能否测的只有两件事**：新区域里有没有腿（腿部标签占比 ≥ 3%）、这次扩展有没有被上限截断。画质分档就由这两项决定。

**身份怎么保证。** 拼合时 `mask == 0` 的像素走 `np.where` 直接拷贝，不做算术混合——算术混合会留下舍入残差，让"逐像素不变"这条不变式失效。校验分两层：

- 硬门：人脸区（腐蚀 3 像素）与全部人物标签区的差异像素占比必须为 0，否则中止、不产出造型。
- 软门：新区域腿部标签占比。占比 < 3% 判定"没画出腿"，换种子重试一次并追加 `both feet visible`；仍失败则返回结果但标 `quality=low`。

**画幅与分段。** SD1.5 在超过 1:1.55 的长条画布上会重复画人。所以 9:16 拆两段：先扩到 1:1.55，对中间结果重新分割，再扩到目标比例。第二段能看见第一段刚画出来的小腿，几何估算更准。3:4 一段就够。

**渐进预览。** `callback_on_step_end` 每 4 步把 latents 解码成一张缩略图，写到 `work/previews/<job>/step-XXXX.png`，文件名带步号所以不会被读到半截。VAE 解码约 80–110 ms，9 张中间图总计约 +1 秒。走 `enable_model_cpu_offload()` 时解码会和 offload hook 抢显存，此时自动降为潜变量投影（3 ms，只有色块）；`safety_checker=None` 也让每张中间图省掉一次 CLIP 判断。

**已知上限。** 没有姿态控制时，"补腿"必然有一定比例的解剖错误：脚部糊成一团、双腿融合、膝盖朝向不对。上面的三项措施（分段、走廊、低强度 IP-Adapter）加上"用下装中位色打底并写进提示词"这一条，把"完全崩坏"压到可接受，但不能消除。要真正解决需要 SDXL-inpainting 或 ControlNet-OpenPose，都需要新增模型，超出本机零新增权重的约束。

**产品副作用。** 渲染器只重绘 512 px 头部裁剪框，会话画面按照片原始比例输出。扩成 3:4 或 9:16 后，对话画面里的脸会明显变小。所以界面上必须提示"建议同时保留一张半身造型"。

## 14. 术语表

| 术语 | 含义 |
|---|---|
| generation | 一轮对话的编号，打断即 +1；所有迟到结果用它判断是否过期 |
| clip | 时间线里的一个播放单元，整句是 `SentenceClip`，流式是 `StreamingSentence` |
| 稳定前缀 | 动作序列里不会再被 overlap/平滑修正的头部 |
| spool | 把 PCM 分块原子写到磁盘的音频缓冲 |
| 租约（lease） | 跨进程的 GPU 使用权记录，带 session、token、pid 签名 |
| 准入（admission） | 用实测峰值判断能否双模型并行 |
| offload | 把权重搬回 CPU 并清空显存缓存 |
| 配对缓冲 | 已就绪且音画都覆盖到的可播时长 |
| NDJSON | 每行一个 JSON 的流式响应，内部 worker 之间使用 |

---

如果只记一句话：**这个项目的核心不是模型，而是"用 PCM 当主时钟、用 generation 当真理、用租约当交通规则"**。模型可以换，这三条不能丢。
